# Databases Workshop — Design

Status: approved for implementation by the user on 2026-11-16 ("just implement, I'll give feedback later"). Decisions the user did not explicitly confirm are marked **(default)**.

## Goal

A 1-hour, hands-on workshop for Road2SWE mentees with little or no SQL experience that (1) shows why database design matters, (2) teaches enough SQL to answer real questions, and (3) gives one short, honest example of when a document database (MongoDB) fits better.

## Constraints

- 60 minutes total; mentees have barely used SQL; venue has wifi.
- Mentees install nothing. They open one link and run real PostgreSQL in the browser (PGlite 0.5.16, which reports PostgreSQL 18.6).
- The instructor runs the same SQL files on local PostgreSQL 16 for the projector.
- Postgres is the only target **(default)**; queries stick to plain, standard SQL where possible because the audience is beginners.
- No data cleaning. MongoDB is shown on slides only, never run.

## Domain and design arc

Domain: club events. Mentees receive a requirements brief, sketch tables on paper in groups, then compare with the reference schema. A 5-minute opener shows the "old sheet" (one flat table) and its visible inconsistencies to motivate the exercise.

Design brief given to mentees:

> USACS wants to replace its sign-up sheet. Students have a NetID, name, email, and graduation year. Clubs host events; each event has a title, date, location, and capacity. Students RSVP to events, and afterwards we record whether they actually came. Your design must answer: Which events are overbooked? Which club has the best turnout? Which events has a given student signed up for?

Reference schema:

```
clubs    (club_id PK, name UNIQUE)
events   (event_id PK, club_id FK→clubs, title, event_date, location, capacity CHECK > 0)
students (netid PK, name, email UNIQUE, grad_year)
rsvps    (netid FK→students, event_id FK→events, attended BOOLEAN, PK(netid, event_id))
signups_sheet (all TEXT, no keys)  -- the old flat sheet, for contrast
```

## Run of show (60 min)

| Time | Segment |
|---|---|
| 0–5 | Old sheet on the projector: `SELECT DISTINCT club_name` returns 10 spellings of 8 clubs; one student has two emails |
| 5–17 | Groups design tables from the brief (10 min), two groups share |
| 17–25 | Reveal reference schema; keys, one-to-many, many-to-many; "try to break it" constraint demo; mentees open the page |
| 25–48 | Queries in three levels (one table → JOIN → GROUP BY); instructor live-codes the first of each level |
| 48–57 | MongoDB segment (slides): per-event sign-up forms with different questions |
| 57–60 | Wrap-up |

## Data

Generated by a deterministic Python script (fixed seed, stdlib only); both the script and the generated `seed.sql` are committed.

| Table | Rows |
|---|---|
| clubs | 8 |
| students | 1,200 (emails `@example.edu`) |
| events | 120, Sep 2025 – Apr 2026 |
| rsvps | ≈9,400, ≈73% attended, turnout varying by club (0.56–0.84) |
| signups_sheet | one row per RSVP plus planted anomalies |

Planted facts (asserted by the generator and by tests):

- Exactly 3 overbooked events; exactly 1 event with zero RSVPs ("Sunrise Photo Walk").
- Exactly 15 students with 3+ RSVPs who never attended; every other student with 3+ RSVPs attended at least once.
- A featured student `sk101` (Scarlet Knight) with exactly 7 RSVPs, including the unique event "Intro to Git".
- In `signups_sheet`: 6 students with two different emails, 3 events listed in two locations, 2 clubs with an inconsistent spelling (10 distinct club names), 5 duplicated sign-up rows.

## Exercises

Stored once in `sql/exercises.sql` with `-- @key value` metadata comments; the page parses that file and psql runs it unchanged.

| # | Level | Question |
|---|---|---|
| 1 | One table (live) | Show 10 students (`LIMIT`) — checked by row/column count only |
| 2 | One table | Events in October 2025, earliest first |
| 3 | One table | How many students graduate in 2028? |
| 4 | One table | Events with capacity over 100 |
| 5 | Joins (live) | Each event's title with its club's name |
| 6 | Joins | Title and date of every event `sk101` RSVP'd to |
| 7 | Joins | Names of students who attended "Intro to Git" |
| 8 | Grouping (live) | Number of events per club |
| 9 | Grouping | RSVPs per event, most popular first |
| 10 | Grouping | Which events are overbooked? |
| 11 | Grouping | Turnout rate per club (fraction 0–1) |
| 12 | Stretch | Events with zero RSVPs |
| 13 | Stretch | Students with 3+ RSVPs who never attended |
| 14 | Stretch | Old sheet: students with more than one email |

Answer checking compares the mentee's last result with the reference query run on the mentee's current database: same column count, same multiset of row values (column names ignored), numeric tolerance 0.005 for non-integers, and, for exercises with `@sorted <col> <asc|desc>`, rows sorted by that column (ties allowed in any order).

"Try to break it" statements live in `sql/break_it.sql` with the expected SQLSTATE for each: foreign key (23503), primary key (23505), check (23514), and the same bad rows succeeding against `signups_sheet`.

## MongoDB segment (slides only)

Each event's sign-up form asks different questions (Hack Night: shirt size, dietary list, GitHub, team; Resume Review: major, resume link, target roles; Poker Night: nothing). SQL attempts: one column per question (mostly NULL, `ALTER TABLE` per form) or a question/answer table (all text, pivots). MongoDB: a `registrations` collection whose documents carry their own answers, with one `find` and one `$group` aggregation. Trade-off slide: documents fit varying shapes read as a whole; SQL fits relationships, joins, and constraints ("Would you store RSVPs in MongoDB?"); Postgres JSONB can do documents too.

## Deliverables (repository root)

- `index.html`, `app.js` (DOM), `workshop.js` (pure logic: exercise/break-it parsing, result comparison, display limits) — static, no build step, PGlite pinned from jsDelivr.
- `sql/schema.sql`, `sql/seed.sql`, `sql/exercises.sql`, `sql/break_it.sql`.
- `scripts/generate_seed.py`.
- `tests/` — Node `node:test` suite using PGlite 0.5.16 from npm (pinned in `package.json`).
- `slides/databases-workshop.pptx` (~14 slides) plus its build script.
- `INSTRUCTOR.md` (run sheet, talking points, steering for common student designs, demo queries, fallback plan) and a short `README.md` (how to serve the page, load into local Postgres 16, regenerate data, run tests).

## Page behavior

- Loads PGlite, runs `schema.sql` then `seed.sql` in memory; shows load status.
- Sidebar lists tables with columns, types, PK/FK markers, and row counts (queried from the catalog, so it never goes stale).
- SQL editor (textarea, Ctrl/Cmd+Enter runs); results table capped at 200 displayed rows with total count; Postgres errors shown verbatim.
- Exercises panel: prompt, hint and answer toggles, "Check my last result" with a specific reason on mismatch; solved state and editor draft remembered in `localStorage` (wrapped in try/catch, optional).
- Reset rebuilds the database from the SQL files.
- Works at phone width; light and dark themes.

## Hosting

Static files: GitHub Pages from the public `Trian27/RTSWEDatabasesWorkshop` repo (https://trian27.github.io/RTSWEDatabasesWorkshop/; requires the user to push), or `python3 -m http.server` locally. A claude.ai Artifact is not viable: PGlite fetches ≈15 MB of WASM/data from jsDelivr at runtime, which the Artifact CSP blocks. `seed.sql` is ≈1.6 MB because the old sheet repeats every RSVP.

## Validation

- Generator determinism: regenerating produces a byte-identical `seed.sql`.
- `npm test`: data loads; planted facts hold; all 14 reference queries run; checker unit cases (order, ties, tolerance, column mismatch); break-it SQLSTATEs.
- Local PostgreSQL 16: schema, seed, exercises, and break-it run in a throwaway database.
- Headless Chrome: the page loads PGlite, builds the database, and renders the sidebar.
- Slides rendered to images and inspected visually.
- Human check: open the page, run exercise 10's answer, see 3 overbooked events, and click Check.

## Out of scope

Index/performance lessons, data cleaning, running MongoDB, club memberships table (mentioned as a stretch discussion only), user accounts or shared state.
